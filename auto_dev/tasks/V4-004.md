# V4-004 Dungeon Reward, Threat Reporting, Return Loop

Purpose: close the playable vertical slice. On a resolved VICTORY the party must receive the dungeon's reward table exactly once, threat must be reported exactly once per clear, alive party returns + arena cleanup follows, and the dungeon stays re-entry-able (`one_shot == false`). This completes preparation → discovery-gated entry (V4-001) → phases (V4-002) → outcome (V4-003) → reward/threat/return (this task).

Reuse: DungeonManager (`get_reward_table_for_dungeon` → table `ne_ruins_clear` with entries `{material, arcane_dust, 3}` and `{potion_material, ghost_essence, 1}`), DungeonRewardTable (`get_entries()`), VillageResources (`has`/`get_amount`, `add` — prefer existing add_food constant-style helpers for the two reward kinds if present, otherwise use the generic add after checking it exists), WaveManager (`report_dungeon_result`, `is_dungeon_clear_applied`, `DUNGEON_CLEARED`), DungeonRuntime (`end_run`, `get_returned_alive_ids`, `run_outcome`, `get_last_outcome`), MercenaryRoster (alive state), DungeonPreparationManager.

Constraints: reward numbers come only from the existing prototype table — do not invent new materials/amounts; no save/load; no inventory UI; no equipment; exactly-once semantics; DungeonRuntime is NOT an autoload. GAME_DESIGN.md untouched.

Requirements:
1. On a cleared run (VICTORY outcome, exactly-once guard from V4-003) apply the dungeon's reward table through VillageResources: each `material` entry adds that `id`/`amount` (arcane_dust +3), each `potion_material` entry adds its `id`/`amount` (ghost_essence +1). Reward grant must be idempotent-within-run and fire alongside the existing single `run_outcome` emit (do not add a second outcome path). Use the reward-bearing table from `DungeonManager.get_reward_table_for_dungeon(dungeon_id)`; if the table is missing, fall through without crashing.
2. Every resolved run returns its party: alive party member ids must flow into `get_returned_alive_ids()` via end_run (already implemented) and still be alive in MercenaryRoster after cleanup; dead members are not returned (already handled by actor death).
3. Run id for the WaveManager bridge stays `dungeon_id` ("ne_ruins"). A cleared run calls `report_dungeon_result(DUNGEON_CLEARED, "ne_ruins")` exactly once → `is_dungeon_clear_applied("ne_ruins") == true`.
4. Re-entry loop: after a CLEARED run the dungeon can be `mark_ready()` again (DungeonManager allows CLEARED→READY, `one_shot == false`), a fresh preparation + IN_PROGRESS + begin_run works, and a second VICTORY increments completion_count to 2 and grants the reward table again (WaveManager dedupe is per dungeon_run_id, so threat reduction stays idempotent — that is existing design, do not change WaveManager).

Validation (tests/v4004_test.gd, `extends SceneTree`, headless, `V4004_ASSERTIONS`/`V4004_RESULT` marker contract): deterministic forced VICTORY via real begin_run + `take_damage(999)` on enemies (V4-003 pattern); assert at least:
- VillageResources gains arcane_dust +3 and ghost_essence +1 after the cleared run (check kindly; if VillageResources has no settlement storage of those ids, follow whatever existing add/get_amount API the test can observe — do not create permanent storage systems; an in-memory VillageResources grant is fine).
- `get_returned_alive_ids()` contains the prep member ids (or enough of them to prove return), and those mercenaries are still alive in MercenaryRoster.
- `is_dungeon_clear_applied("ne_ruins") == true`.
- Re-entry: mark_ready → new prep → IN_PROGRESS → begin_run → VICTORY → completion_count == 2 and reward granted a second time.

Exit quit(0) only after markers. Also required: `tests/baseline_3d_health_test.gd` passes.
